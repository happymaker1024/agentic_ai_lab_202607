# 강사용 Agentic AI 강의 가이드

## 1. 이 가이드의 목적

이 가이드는 `track1_core` 바로 아래의 14개 실습 노트북을 강사 교육에 활용할 때,
개념과 코드를 너무 어렵게 전달하지 않도록 강의 흐름을 재구성한 자료다.

대상은 Python과 Jupyter Notebook의 기본 사용법은 알지만 Agentic AI, LangGraph,
RAG, Memory, HITL은 처음 접하는 강사로 가정한다.

강의의 목표는 API와 문법을 모두 암기시키는 것이 아니다. 다음 세 문장을 설명하고
실습으로 확인할 수 있게 만드는 것이 핵심이다.

1. **LLM은 판단을 제안하고, 애플리케이션은 실행하고 통제한다.**
2. **Agent는 목표를 위해 다음 행동을 동적으로 선택하지만, 항상 Workflow보다 좋은 것은 아니다.**
3. **좋은 Agentic AI는 자율성뿐 아니라 상태, 종료 조건, 근거, 사람의 개입을 함께 설계한다.**

## 2. 전체 과정을 한 문장으로 설명하기

> Agentic AI는 사용자의 목표와 현재 상태를 바탕으로 다음 행동을 선택하고, 필요한
> 도구와 지식을 사용하며, 결과를 관찰해 계속할지 멈출지를 결정하는 AI 시스템이다.

처음부터 `StateGraph`, `ToolNode`, `Checkpointer` 같은 용어를 나열하지 않는다. 먼저
다음 네 단계로 전체 과정을 보여준 뒤, 각 단계에서 필요한 기술을 하나씩 소개한다.

| 단계 | 학습자의 질문 | 관련 노트북 |
|---|---|---|
| 1. 답하기 | AI App, Workflow, Agent는 무엇이 다른가? | 01-1, 01-2 |
| 2. 행동하기 | LLM은 어떻게 Tool을 고르고 여러 번 행동하는가? | 01-3, 01-4 |
| 3. 흐름 관리하기 | 상태·단계·분기·반복을 어떻게 구조화하는가? | 02-1, 02-2, 02-3 |
| 4. 신뢰할 수 있게 만들기 | 지식·기억·사람의 확인을 어떻게 연결하는가? | 03-1~05-1 |
| 5. 직접 설계하기 | 내 문제에는 어느 정도의 자율성이 필요한가? | 06 |

## 4. 매 노트북을 가르치는 공통 순서

각 노트북을 다음 여섯 단계로 반복하면 학습자가 새로운 API보다 문제 해결 흐름에
집중할 수 있다.

1. **문제 제시** — “기존 방식으로 무엇이 안 되는가?”
2. **그림 설명** — 코드를 보기 전에 네모와 화살표로 실행 흐름을 그린다.
3. **정상 실행** — 가장 단순한 성공 사례 하나를 실행한다.
4. **State 또는 로그 관찰** — 최종 답변보다 중간 판단과 실행 경로를 본다.
5. **의도적 실패** — 잘못된 Tool, 반복, 근거 부족, 중복 알림을 재현한다.
6. **안전장치 추가** — 검증, 기본 경로, 최대 반복, HITL 등으로 수정한다.

강사가 모든 코드를 읽어주는 방식은 피한다. 한 노트북에서 학습자가 직접 완성할 TODO는
핵심 함수 하나만 선택하고, 나머지는 실행 흐름과 결과 해석에 집중한다.

공통 질문은 다음 두 개면 충분하다.

- “지금 다음 단계를 결정한 주체는 개발자 규칙인가, LLM인가?”
- “이 단계가 실패하거나 끝나지 않으면 어떤 안전장치가 필요한가?”

## 5. 노트북별 강의 가이드와 설명 대본

### 5.1 `01-1_ai_app_workflow_agent.ipynb`

**핵심 질문**

> 같은 결과를 만들더라도 실행 경로를 누가 결정하는가?

**쉬운 비유 — 식당**

- AI App: 손님 질문에 직원 한 명이 바로 답한다.
- Workflow: 정해진 조리법대로 전처리, 조리, 담기를 수행한다.
- Agent: 주문을 보고 주방장이나 바리스타 중 누구에게 일을 맡길지 매니저가 판단한다.

**설명 대본**

> 세 구조의 차이는 AI를 몇 번 호출했는지가 아니라 실행 경로를 누가 결정하느냐에
> 있습니다. AI App은 요청을 바로 모델에 전달합니다. Workflow는 개발자가 단계와
> 순서를 미리 고정합니다. Agent는 현재 요청을 보고 필요한 Tool과 다음 행동을
> 동적으로 고릅니다. 그래서 Agent가 가장 유연하지만, Tool을 잘못 선택하거나 필요한
> 단계를 빠뜨릴 수 있습니다. 단순하고 정해진 일에는 Workflow가 더 싸고 예측 가능할
> 수 있습니다.

**시연 포인트**

- 같은 문서와 요청을 세 함수에 넣고 `executed_steps`, `selected_tools`를 비교한다.
- 답변 문장보다 “실제로 어떤 단계가 실행됐는가”를 먼저 보게 한다.
- 실패 실험에서 Agent가 필요한 Tool을 누락하는 장면을 반드시 보여준다.

**반드시 교정할 오해**

> Agent는 Workflow의 상위 버전이 아니다. 유연성과 통제 가능성 사이의 다른 설계
> 선택이다.

**다음 장 연결**

> Agent가 안정적으로 판단하려면 LLM의 자유형 문장을 프로그램이 읽을 수 있는
> 데이터로 바꿔야 한다.

### 5.2 `01-2_llm_message_structured_output.ipynb`

**핵심 질문**

> LLM의 답을 사람이 읽는 문장이 아니라 프로그램이 믿고 사용할 데이터로 만들려면?

**쉬운 비유 — 신청서와 접수 직원**

자유형 출력은 민원인이 빈 종이에 자기 방식대로 적어 내는 것이다. JSON으로 써달라는
요청은 “이 양식처럼 써주세요”라는 안내다. Pydantic 검증은 접수 직원이 필수 항목,
자료형, 허용값을 실제로 확인하는 과정이다.

**설명 대본**

> 모델에게 JSON으로 답해 달라고 요청하는 것과 Structured Output은 다릅니다.
> 요청은 형식을 안내할 뿐이고, Structured Output은 Schema를 정의하고 결과를 Parsing한
> 뒤 Validation합니다. 중요한 점은 Pydantic이 답의 사실 여부를 확인하는 기능이
> 아니라는 것입니다. 필드가 있는지, 자료형이 맞는지, 허용된 값인지만 확인합니다.
> 실패하면 무한 재시도하지 말고 제한된 재시도나 안전한 기본값으로 처리해야 합니다.

**시연 포인트**

- System 메시지 유무와 Zero-shot/Few-shot 결과를 짧게 비교한다.
- 자유형 출력 → JSON 요청 → Pydantic 검증의 세 단계를 순서대로 보여준다.
- `ValidationError`를 “실패”가 아니라 “문제를 감지한 성공적인 안전장치”로 설명한다.

**반드시 교정할 오해**

> 형식 검증은 내용이 참이라는 보증이 아니다.

**다음 장 연결**

> 이제 LLM이 안정된 이름과 인자로 행동을 제안하게 하고, 실제 기능을 연결해 보자.

### 5.3 `01-3_tool_calling_basic.ipynb`

**핵심 질문**

> LLM이 할 수 없는 계산, 파일 조회, 검색을 어떻게 외부 기능에 맡기는가?

**쉬운 비유 — 콜센터 상담원과 현장 기사**

상담원인 LLM은 어떤 기사에게 어떤 작업을 요청할지 결정한다. 실제 계량기 점검은
현장 기사가 수행한다. 작업 결과가 다시 상담원에게 돌아와야 고객에게 최종 답을
설명할 수 있다.

**설명 대본**

> LLM은 Tool을 직접 실행하지 않습니다. Tool 이름과 인자를 담은 Tool Call을
> 제안합니다. 애플리케이션이 인자를 검증하고 실제 Python 함수를 실행한 뒤, 그 결과를
> Tool Message로 모델에 돌려줍니다. 모델은 이 결과를 읽고 최종 자연어 응답을 만듭니다.
> 따라서 오류도 Tool 선택 오류, 인자 검증 오류, 실제 실행 오류로 나눠서 봐야 합니다.

**칠판에 남길 흐름**

```text
User → LLM의 Tool Call 제안 → 앱의 검증·실행 → Tool Message → LLM 최종 답변
```

**시연 포인트**

- `ai_message.tool_calls`에서 이름과 인자를 직접 확인한다.
- Tool Message를 돌려주지 않았을 때와 돌려줬을 때를 비교한다.
- 존재하지 않는 Tool, 누락 인자, 잘못된 자료형, 0으로 나누기 같은 실패를 구분한다.
- 계산 Tool이 `eval()`을 그대로 사용하지 않는 이유를 보안 관점에서 짚는다.

**반드시 교정할 오해**

> LLM의 제안은 실행 명령이 아니라 검증해야 할 입력 데이터다.

**다음 장 연결**

> Tool을 한 번 쓰는 것으로 끝나지 않고, 첫 결과를 보고 두 번째 행동을 정해야 하는
> 문제로 확장한다.

### 5.4 `01-4_agent_loop_react.ipynb`

**핵심 질문**

> 첫 행동의 결과를 보고 다음 행동을 다시 결정하게 하려면?

**쉬운 비유 — 내비게이션**

내비게이션은 출발할 때 전체 경로를 보여주지만, 실제 이동 중에는 현재 위치와 교통
상황을 관찰해 다음 길을 다시 판단한다. 목적지 도착은 논리적 종료이고, 연료가 떨어지기
전에 운행을 강제 중단하는 것은 최대 반복 횟수라는 안전장치다.

**설명 대본**

> Agent Loop는 Plan, Act, Observe, Evaluate를 반복합니다. 중요한 것은 Observation이
> 다음 Plan에 들어간다는 점입니다. 이전 결과를 보지 않으면 같은 행동을 반복할 수
> 있습니다. `finish`는 목표를 달성했다는 논리적 종료 조건이고, `max_iterations`는
> 시스템을 보호하는 비상 정지 장치입니다. 최대 횟수에 도달한 것은 정상 완료가 아니라
> 실패로 기록해야 합니다.

**시연 포인트**

- `128 ÷ 4`의 결과를 다음 `+17` 계산에 사용하는 과정을 한 단계씩 출력한다.
- 고장 난 Plan 함수로 동일 행동 반복을 재현한다.
- `detect_repeated_action()`과 `max_iterations`의 역할 차이를 질문한다.

**반드시 교정할 오해**

> 반복 횟수 제한은 Agent가 문제를 해결했다는 뜻이 아니라, 해결하지 못했을 때의
> 안전장치다.

**다음 장 연결**

> 지금까지 직접 만든 상태 딕셔너리와 반복문을, 단계가 늘어나도 추적할 수 있는
> Graph 구조로 옮긴다.

### 5.5 `02-1_langgraph_state_node_edge.ipynb`

**핵심 질문**

> 여러 처리 단계가 공유하는 데이터와 실행 순서를 어떻게 명시적으로 표현하는가?

**쉬운 비유 — 공용 작업판**

State는 팀이 함께 보는 작업판, Node는 각 담당자, Edge는 업무가 다음 담당자에게
전달되는 순서다. Edge는 길만 정하고 데이터를 보관하지 않는다.

**설명 대본**

> State는 여러 Node가 공유하는 작업 데이터입니다. 각 Node는 State 전체를 새로
> 만들지 않고 자신이 변경한 필드만 반환합니다. Edge는 데이터가 아니라 실행 순서를
> 정의합니다. Compile은 설계도를 실행 가능한 공정으로 만드는 단계이고, Invoke는
> 실제 작업물을 넣어 한 번 가동하는 단계입니다. 이 구조의 장점은 어느 Node가 어떤
> 값을 읽고 썼는지 추적하기 쉬워진다는 것입니다.

**시연 포인트**

- 실행 전후 State를 나란히 놓고 바뀐 필드만 표시한다.
- Node의 반환 키를 일부러 틀려 조용히 갱신되지 않는 문제를 관찰한다.
- `START → analyze_input → generate_answer → END`만 먼저 그린 뒤 코드를 본다.

**반드시 교정할 오해**

> State는 전역변수가 아니고, Edge는 데이터를 운반하는 저장소가 아니다.

**다음 장 연결**

  보여준다.

- 바뀐 선호를 새 레코드로 계속 추가했을 때 모순이 생기는 실패를 보여준다.

**반드시 교정할 오해**

> Memory는 모든 대화의 영구 보관소가 아니다.

**다음 장 연결**

> 멈추는 기능이 필요하다.

### 5.12 `04-2_checkpoint_human_in_the_loop.ipynb`

**핵심 질문**

> Agent가 추측하면 위험한 지점에서 어떻게 멈추고 사람의 답으로 이어서 실행하는가?

**쉬운 비유 — 책갈피와 승인 게이트**

Checkpoint는 읽던 위치와 메모를 보존하는 책갈피다. HITL은 중요한 문을 통과하기 전에
사람의 승인을 받는 게이트다. 재개할 때 해당 Node를 처음부터 다시 실행하므로, 이미
보낸 알림의 영수증을 Graph 밖에 남겨야 중복을 막을 수 있다.

**설명 대본**

> `interrupt()`는 실패가 아니라 의도적인 일시 정지입니다. Checkpointer가 State를
> 저장하고, 사용자의 답을 같은 `thread_id`의 `Command(resume=...)`로 전달하면 실행을
> 이어갑니다. 주의할 점은 재개 시 interrupt를 호출한 Node가 처음부터 다시 실행된다는
> 것입니다. 알림 전송처럼 외부에 영향을 주는 코드는 중복될 수 있으므로 State 내부
> 플래그가 아니라 외부 저장소의 멱등성 키로 보호해야 합니다.

**시연 포인트**

- 정보가 충분한 정상 경로와 부족해서 멈추는 경로를 비교한다.
- `__interrupt__`에 담긴 질문을 직접 확인한다.
- 다른 `thread_id`로 재개했을 때 이어지지 않는 것을 보여준다.
- 중복 알림을 재현한 후 `thread_id` 기반 외부 기록으로 한 번만 실행되게 한다.

**반드시 교정할 오해**

> Checkpoint는 장기 기억이 아니며, State 안의 플래그만으로 interrupt 이전 부작용의
> 중복을 막을 수 없다.

**다음 장 연결**

> 지금까지 만든 분기, Tool Agent, RAG, HITL을 하나의 시스템에서 역할별로 결합한다.

**쉬운 비유 — 건축 설계**

코드를 먼저 쓰는 것은 평면도 없이 벽돌부터 쌓는 것과 같다. 사용자의 목표, 필요한
정보, 상태, 행동, 위험 지점, 종료 조건을 먼저 정한 뒤 Graph를 만든다.

**설명 대본**

> 마지막 과제의 목적은 지금까지 본 기능을 모두 넣는 것이 아닙니다. 먼저 해결할 문제와
> 성공 기준을 정하고, State에 무엇을 보관할지, 어떤 Node가 한 가지 책임을 맡을지,
> 어디에서 규칙 분기와 LLM 판단을 사용할지 결정합니다. RAG, Memory, HITL은 필요할
> 때만 선택합니다. 좋은 결과물은 기능이 많은 Agent가 아니라 실행 경로와 실패 대응을
> 설명할 수 있는 Agent입니다.

**워크숍 순서**

1. 사용자와 문제를 한 문장으로 정의한다.
2. 입력, 중간 데이터, 최종 결과를 State 표로 작성한다.
3. Node를 동사 하나로 이름 붙이고 단일 책임을 확인한다.
4. 규칙 기반 Routing과 LLM 판단 지점을 다른 색으로 표시한다.
5. 정상, 정보 부족, Tool 실패 시나리오를 최소 하나씩 작성한다.
6. Graph를 그린 뒤에만 Notebook TODO를 구현한다.

**평가 기준 예시**

| 항목 | 배점 |
|---|---:|
| 문제와 성공 기준의 명확성 | 15 |
| State와 Node의 책임 분리 | 20 |
| Routing·Tool 선택의 근거 | 15 |
| RAG 또는 외부 지식 활용의 적절성 | 15 |
| Memory·HITL 사용의 적절성 | 15 |
| 종료 조건과 실패 대응 | 10 |
| 실행 흐름 설명과 회고 | 10 |

## 6. 강사가 자주 받을 질문과 짧은 답변

### “Workflow도 AI가 들어가면 Agent 아닌가요?”

용어의 범위는 자료마다 다르다. 이 과정에서는 수업을 위해 실행 경로가 개발자에 의해
고정되면 Workflow, 현재 상태에 따라 LLM이 다음 행동이나 Tool을 동적으로 선택하면
Agent로 구분한다. 중요한 것은 이름보다 **결정 주체와 통제 범위**를 밝히는 것이다.

### “LLM이 Tool을 호출한다는 말은 틀린가요?”

일상적인 표현으로는 사용할 수 있지만, 정확히는 LLM이 Tool 이름과 인자를 제안하고
애플리케이션이나 실행 환경이 실제 Tool을 실행한다.

### “State가 곧 Memory인가요?”

아니다. State는 현재 Graph의 작업 데이터다. Checkpointer로 같은 thread에서 이어질 수
있지만, 여러 thread에서 장기간 사용할 정보는 Store 기반 Memory로 별도 관리한다.

### “유사도 0.9면 거의 정답 아닌가요?”

아니다. 유사도는 질문과 문서가 벡터 공간에서 상대적으로 가깝다는 뜻이다. 정답일 확률이
아니므로 실제 문서가 질문의 근거를 포함하는지 확인해야 한다.

### “Agentic RAG가 일반 RAG보다 좋은 것 아닌가요?”

근거 검증과 재검색이라는 안전장치를 얻지만 LLM 호출, 비용, 지연, 판단 오류 가능성도
늘어난다. 문서와 질문이 단순하면 일반 RAG가 더 적절할 수 있다.

### “사람이 개입하면 자동화의 의미가 줄지 않나요?”

사람이 모든 단계를 처리하는 것과, 위험하거나 정보가 부족한 경계에서만 확인하는 것은
다르다. HITL은 자동화를 포기하는 것이 아니라 안전하게 적용 범위를 넓히는 방법이다.

### “temperature=0이면 같은 결과가 항상 나오나요?”

대부분 더 안정적으로 재현되지만 100% 결정론을 보장하는 것은 아니다. 중요한 경로는
LLM 응답의 우연성에만 의존하지 말고 Schema, 규칙, 기본 경로, 테스트로 보호해야 한다.

## 7. 라이브 실습 운영 체크리스트

### 수업 전

- 프로젝트의 환경 점검 노트북을 실행한다.
- API 키와 모델 접근 권한을 확인한다.
- 동일한 Kernel과 프로젝트 루트에서 실행되는지 확인한다.
- Chroma Collection의 기존 데이터가 실습 결과에 영향을 주는지 확인한다.
- 정상 사례, 실패 사례, 수정 사례를 각각 한 번 미리 실행한다.
- API 장애에 대비해 저장된 출력이나 로그로 설명할 수 있게 준비한다.

현재 저장된 노트북 상태를 확인한 결과, 저장된 오류 출력은 14개 모두 없다. 다만 다음
세 노트북은 코드 셀의 실행 결과가 저장되어 있지 않으므로 라이브 강의 전에 반드시
사전 실행한다.

- `02-1_langgraph_state_node_edge.ipynb`
- `03-2_embedding_vector_retrieval.ipynb`
- `06_my_agentic_ai_worksheet.ipynb`

01-1, 01-2, 01-3 일부 코드 셀의 미실행 상태는 TODO나 선택 실행 셀일 수 있으므로
강의에서 사용할 경로를 기준으로 다시 확인한다.

### 수업 중

- 최종 답변보다 `State`, `messages`, `executed_steps`, `route`, `retry_count`를 먼저 본다.
- 긴 출력은 모두 읽지 않고 이번 개념과 관련된 필드만 표시한다.
- 모델 응답이 예시와 다르면 오답으로 단정하지 말고 실행 경로와 안전장치를 확인한다.
- 한 노트북에서 라이브 코딩은 핵심 TODO 하나로 제한한다.
- 실패 실험 뒤에는 반드시 “운영 환경에서는 어떻게 막을 것인가?”를 질문한다.

### 수업 후

- 학습자에게 API 이름을 암기시키는 문제보다 실행 경로를 설명하게 한다.
- 최종 과제에서는 기능 수보다 결정 주체, 종료 조건, 실패 복구의 타당성을 평가한다.

## 8. 강의에서 반복해서 사용할 핵심 문장

다음 문장은 여러 장에서 반복해도 좋다.

1. **LLM은 판단을 제안하고, 애플리케이션은 실행한다.**
2. **State는 데이터이고, Edge는 경로다.**
3. **Routing은 다음 Node를 고르고, Tool Selection은 사용할 기능을 고른다.**
4. **Tool 결과는 다시 Agent에게 돌아가야 다음 판단에 반영된다.**
5. **최대 반복 횟수는 성공 조건이 아니라 비상 정지 장치다.**
6. **유사도는 정답 확률이 아니다.**
7. **검색 결과가 있다는 것과 근거가 있다는 것은 다르다.**
8. **Memory는 모든 대화를 저장하는 곳이 아니다.**
9. **Agent가 모르면 추측하게 하지 말고, 근거 부족을 알리거나 사람에게 묻게 한다.**
10. **가장 좋은 Agent는 가장 자율적인 Agent가 아니라, 필요한 만큼만 자율적인 Agent다.**

## 9. 전체 과정 마무리 대본

> 우리는 단순한 LLM 호출에서 시작해 Tool을 사용하는 방법, 결과를 관찰하며 반복하는
> Agent Loop, 그리고 이를 State, Node, Edge로 구조화하는 방법을 살펴봤습니다. 이후
> 문서를 검색 가능한 지식으로 만들고, 검색 근거를 평가하며, 필요한 기억만 남기고,
> 위험하거나 정보가 부족한 지점에서는 사람에게 묻게 했습니다. Agentic AI의 핵심은
> 모델에게 모든 결정을 맡기는 것이 아닙니다. 변화가 많은 판단에는 제한된 자율성을
> 주고, 중요한 경계에는 규칙, 검증, 종료 조건, 근거와 사람의 확인을 두는 것입니다.
> 이제 여러분이 설계할 때 가장 먼저 물어야 할 질문은 ‘어떤 Agent를 만들까?’가 아니라
> ‘이 문제에서 무엇을 고정하고, 무엇을 AI가 판단하게 하며, 실패하면 어떻게 안전하게
> 멈출까?’입니다.
